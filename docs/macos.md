# macOS

macOS is the third system beside Windows and Linux: one source tree, the system's own parts
behind the same platform seam (`crates/app/src/platform/macos/`, with what it shares with
Linux in `platform/unix/`; `player_core::output` for sound; `library::dirwatch` for folder
watching). Windows and Linux are unchanged by it.

**State of the port.** The macOS code, its packaging and its CI jobs were written on Windows,
without a Mac. What could be checked there was: the release tool's macOS code type-checks
for `aarch64-apple-darwin` and its pure parts (Info.plist, the `.icns` container, reading
`otool`'s output) are unit-tested on Windows; the workflows pass `actionlint` and
`shellcheck`. The player has since been built and tested with Core Audio on Apple Silicon.
The playback results and the remaining platform checks are listed under
[What was tested](#what-was-tested-and-what-was-not).

## Building

On macOS 11 or newer, Apple Silicon or Intel:

    xcode-select --install                 # the Xcode command line tools (clang, codesign, hdiutil...)
    brew install cmake                     # for libopus
    rustup toolchain install 1.99.1        # the same toolchain as Windows and Linux
    cargo build -p marquee-player --release      # target/release/MarqueePlayer

Xcode itself is not needed, nor Homebrew beyond CMake (any CMake on PATH does). The first
build downloads Skia's prebuilt binaries for macOS, as on the other systems. AppKit and
Foundation are reached through the objc2 bindings, which need no SDK headers and no
bindgen. Tests: `cargo test --workspace --release`, with `ffmpeg` on PATH for the fixtures
(`brew install ffmpeg-full` and put its `bin` on PATH: Homebrew's plain `ffmpeg` has no libvorbis encoder, which the Ogg Vorbis fixtures need; ffmpeg 8 or newer for the MP4 gapless check). `cargo xtask check`
runs the checks before a push as on the other systems.

`cargo build` and `cargo xtask build` make a bare binary, not an app bundle: it runs from a
terminal (`./MarqueePlayer`), without the bundle's icon, identifier and document types.
The app bundle is made by `cargo xtask release` ([The package](#the-package)).

## Running, and what it needs

macOS 11 Big Sur or newer (`LSMinimumSystemVersion`, and the deployment target the release
builds for). Everything the binary links is part of macOS: the system library, Core Audio,
AppKit, Foundation, Metal and the other frameworks; the release refuses a binary that links
anything else (a Homebrew library picked up by a build script, for instance). The release
package is for **Apple Silicon only** for now; `cargo xtask release` on an Intel Mac makes an
`x86_64` package of the same kind, but none is built or published.

## The package

`cargo xtask release` on a Mac (`crates/xtask/src/release/macos.rs`) makes
`dist/MarqueePlayer-<version>-macos-arm64.dmg` (`x86_64` on an Intel Mac), a disk image with
`MarqueePlayer.app` and a link to `/Applications` to drag it onto, and keeps the binary
before stripping and its `MarqueePlayer.dSYM` in `dist/symbols/<version>/macos/` (never
shipped: they hold the build's paths; they symbolicate a crash report). The bundle:

    MarqueePlayer.app/Contents/
        Info.plist                      written by the release (below)
        PkgInfo
        MacOS/MarqueePlayer             the dist build, stripped (strip -S -x)
        Resources/MarqueePlayer.icns    the app's icon art (src/tray/icon_art.rs) on macOS' icon grid
        Resources/README.md             packaging/user-README.md
        Resources/LICENSE.txt           packaging/LICENSE.txt
        Resources/THIRD-PARTY-NOTICES.txt
        _CodeSignature/                 the signature

- **Info.plist** is generated by the release (`info_plist`), not kept in the tree: bundle
  identifier `app.marqueeplayer.MarqueePlayer` (the app's `platform::APP_ID`), name "Marquee
  Player", the release number as `CFBundleShortVersionString` and `CFBundleVersion`,
  `LSMinimumSystemVersion` 11.0, `NSHighResolutionCapable`, the Music category, a copyright
  line, and one document type (role Viewer, rank Alternate: Finder offers the app under Open
  With but never makes it the default player) for the extensions the scanner takes
  (`library::scan::AUDIO_EXTS`; a test keeps the two lists equal, and the identifier equal to
  `APP_ID`). Not `LSUIElement`: the app has a Dock icon. Playlist files are not a document
  type: the app imports them from a drop on its window, not from a launch.
- **The icon** is the same artwork as the Windows and Linux icons, drawn at 824 of 1024 units
  in the middle of the square, as Apple's grid has it, so it sits in the Dock at the size of
  the system's icons. The `macos_icon` example (`crates/app/examples/macos_icon.rs`) writes the
  PNGs; the release packs them into the `.icns` itself (entries `icp4`, `icp5`, `ic07` to
  `ic14`), so `iconutil` is not needed.
- **The signature** is ad hoc (`codesign --force --deep -s -`): Apple Silicon runs no
  unsigned code, and an ad-hoc signature needs no Apple account. It says nothing about who
  made the app, so Gatekeeper treats the download as from an unidentified developer
  ([First launch](#first-launch)). The release then verifies the signature
  (`codesign --verify --deep --strict`) and starts the signed binary once (`--version`).
- **A real identity**: with `MP_CODESIGN_IDENTITY` set to a "Developer ID Application: ..."
  identity in the keychain, the bundle is signed with it (hardened runtime, secure
  timestamp), and the disk image too. Notarisation (`xcrun notarytool submit --wait`, then
  `xcrun stapler staple`) is not done: it needs an Apple developer account. The place is
  marked in `macos.rs` (`sign`).
- **The disk image** is `hdiutil create -fs HFS+ -format UDZO` from a folder with the bundle
  (copied with `ditto`, which keeps the signature intact) and the `/Applications` link, then
  `hdiutil verify`. `hdiutil` is tried three times: it fails now and then with "Resource busy"
  on a loaded machine.

What the release checks besides what it checks on every system ([Version and
releases](releases.md#version-and-releases)): the Xcode command line tools (it takes Apple's
tools from `/usr/bin`, never Homebrew's binutils), the libraries the binary links (`otool -L`:
only `/usr/lib` and `/System/Library`), the minimum macOS it was built for (`otool -l`,
`LC_BUILD_VERSION`: 11.0; the build sets `MACOSX_DEPLOYMENT_TARGET`), `plutil -lint` on the
Info.plist, and the leaked-path check on the stripped binary.

### First launch

The app is signed ad hoc and not notarised, so the first time it is opened from a download,
Gatekeeper stops it ("Apple could not verify..." or "...cannot be opened because the developer
cannot be verified"). Once allowed, it opens normally from then on. Either:

- **macOS 15 Sequoia and later**: open it once (it is refused), then System Settings > Privacy
  & Security, scroll to Security, **Open Anyway** next to Marquee Player, and confirm.
- **macOS 11 to 14**: right-click (or Control-click) the app in Applications > **Open**, then
  Open in the dialog. (Sequoia removed this shortcut.)
- **Any version, in Terminal**: `xattr -dr com.apple.quarantine /Applications/MarqueePlayer.app`,
  which removes the download's quarantine mark (do this only for a copy you downloaded from
  this project's own releases).

## What is different on macOS

The owner's decisions for the port, and how the code carries them out:

- **The window: the system's traffic lights over the app's own caption**
  (`platform/macos/window.rs`). The title bar is transparent and the content runs under it,
  so the page reaches the top edge as on Windows and Linux, while close, minimize and zoom are
  the system's buttons at the top left; the app hides its own caption buttons and keeps that
  corner free (the sidebar shows no "Marquee" title there). Dragging the caption strip moves the window (AppKit's own drag), a double click
  does what System Settings > Desktop & Dock says (zoom, minimize or nothing); resizing, the
  shadow and the rounded corners are the system frame's. There is no window menu.
- **Command in the role of Ctrl** for every shortcut (as Slint makes it), the remappable pin
  keys included; **Cmd+Q quits** (as do the Dock's Quit and logging out, which end the session
  as Windows' session end does).
- **Sound: Core Audio, shared mode only** (`player-core/src/output/coreaudio.rs`): an output
  audio unit (AUHAL) on the chosen device or the system default, fed from a lock-free ring by
  Core Audio's real-time callback (no allocation, locking or blocking call in it). The ring
  itself is kept filled to 100 ms or four callbacks, whatever the device holds beyond it
  (`output/ring.rs`): a high-latency output (Bluetooth, AirPlay, HDMI) no longer leaves it a
  sliver per callback, which crackled for the rest of the stream. Seeks and stops cut in the
  callback, so the depth does not delay them; a pause, the volume and the equalizer act after
  it. Whether the device is still there is asked after a device notification, not on every
  write. The log says the output's transport (built-in, Bluetooth, USB...) and the parts of
  its delay at every open, each underrun with where it fell in the track, and a summary at
  most every 10 s when it changed (underruns, the ring's lowest, the device's delay and
  quantum); Copy diagnostics' "Sound:" line has the underruns and the delay. The stream
  is the track's own rate; the unit converts it to the device's rate (set in Audio MIDI
  Setup), which the technical details show, so the app never resamples. Gapless within a
  rate; seek, play-now and stop are click-free cuts (5 ms fades), as with PipeWire. Devices are
  listed by UID and name and followed as they come and go and as the default changes (a
  chosen device that is gone means the default meanwhile, and back when it returns). **No
  exclusive or bit-perfect output**: hog mode and switching the device's rate are not
  implemented; Settings > Output says the setting is not available on macOS.
- **Secrets in a 0600 file**, not the Keychain: the server and ListenBrainz credentials are
  written as on Linux (`platform/unix/secret.rs`), readable by the user only.
- **Data in `~/Library/Application Support/MarqueePlayer`** (settings, library, state, log),
  the caches (safe to delete) in `~/Library/Caches/MarqueePlayer`. There is no portable
  edition on macOS; `MP_DATA_DIR` still puts everything in one folder.
- **Media keys and Now Playing through souvlaki** (`platform/macos/media.rs`): Control
  Center's Now Playing, the lock screen, the Touch Bar and the keyboard's media keys, as
  souvlaki serves Windows' media overlay.
- **The tray is a menu-bar status item** (`platform/macos/tray.rs`, Slint's `SystemTrayIcon`):
  a click opens its menu, as every status item's does, with the same menu as on the other
  systems; there is no click-to-play, middle button or wheel on it. Closing the window keeps
  the app in the menu bar when that is set; clicking the Dock icon brings the window back.
  The macOS menu-bar icon stays static during playback.
- **Open at login through a LaunchAgent** (`platform/macos/integration.rs`):
  `~/Library/LaunchAgents/app.marqueeplayer.MarqueePlayer.plist`, which starts the bundle's
  executable in the menu bar. System Settings > General > Login Items lists it as a background
  item; turned off there, it does not start.
- **One instance per data folder** through a Unix socket, as on Linux (`platform/unix/instance.rs`).
  Files opened from the Finder, dropped on the Dock icon or chosen in Open With start no
  second process: AppKit sends the running app an open-documents Apple event, which the app
  takes from the Apple event manager (winit does not pass it on) and handles as a second
  launch's files (`platform/macos/appleevents.rs`).
- **Files**: the folder watcher is an FSEvents stream per watched folder (`library::dirwatch`,
  `fsevents.rs`; it reports real paths, given back under the path asked for). File names are
  compared as the file system does, case and Unicode normalisation ignored. Tag editing keeps a
  file's extended attributes, as on Linux. The scanner checks the AppleDouble signature
  on audio filenames starting with `._` so it skips Finder metadata and keeps genuine tracks.
- **The Finder, links, the clipboard** (`platform/macos/shell.rs`): "Show in Finder"
  (`open -R`), folders and web pages with `open`, the general pasteboard for Copy and Paste.
- **Rendering.** macOS defaults to Skia on Metal with live backdrop blur. Core Animation
  can draw the moving spectrum beneath the controls, including behind a stationary menu
  or submenu. Skia draws the whole scene while sidebars slide. During steady playback,
  the elapsed time and seek fill can update independently of the rest of the window.
  The ordinary slider handles hovering, dragging and keyboard input.
  For lower memory use, launch with `SLINT_BACKEND=winit-software`. This selects
  retained tiles at the display's native scale and pre-blurred album art behind the
  transport. Settings → About reports the window surface in use.
- **Fonts** use San Francisco unless `theme.toml`'s `font_family` names another.
- **Words**: "Show in Finder", "Exclusive mode" (not available), "Open at login"
  (`platform::Words`).
- **Test windows** (`MP_WINDOW=secondary`, `platform/macos/devwindow.rs`) open on the second
  display when there is one and never take the focus, as on Windows.

## CI

`.github/workflows/desktop.yml` runs `cargo xtask check` on `macos-latest` (Apple Silicon)
by hand (Actions > Desktop > Run workflow, choosing the systems) and from every release that
builds macOS; nothing runs for a push or a pull request, on any system. The job installs CMake and
ffmpeg from Homebrew when the image lacks them. `.github/workflows/release.yml` builds the disk
image on `macos-latest` with the other packages ([Version and
releases](releases.md#version-and-releases)).

## What was tested, and what was not

Tested, on Windows:

- `cargo check -p xtask --target aarch64-apple-darwin` (the release tool's macOS code compiles
  for macOS) and clippy over it with `-D warnings`;
- the unit tests of `release/macos.rs`: the Info.plist's keys and that it names the app's
  `APP_ID` and the scanner's extensions, the `.icns` container (layout, lengths, refusing a PNG
  of the wrong size), reading `otool -L` and `otool -l`;
- the `macos_icon` example's PNGs (it runs anywhere), looked at;
- the two workflows with `actionlint` 1.7.7 and `shellcheck` 0.10, and their shell steps
  (choosing the systems, comparing the numbers) run in bash with made-up inputs.

On an Apple M4 Max running macOS 26.7, a local release build played stereo FLAC through
Core Audio with Home, the visualizer and the hidden window. In a pre-scanned queue of
44 distinct 1200 px album covers, with menu-bar animation off in both builds, physical
footprint peaked at 403 MiB in beta 2026.11.20.2. Two optimized runs peaked at 186 and
109 MiB. Fifteen seconds into the last track the beta held 259 MiB and the optimized
runs held 80 and 48 MiB.
The audio log reported zero underruns. See the [playback benchmark](testing.md#measurement-and-test-hooks).

A separate 32-second comparison used the same local stereo FLAC passage, 44-track queue,
pinned sidebars and Classic visualizer in a 1440 × 900 point Retina window. The preceding
beta averaged 35.5% of one core with a median physical footprint of 787 MiB. The tiled
renderer with the Core Animation spectrum averaged 3.1% and 142 MiB. Retired instructions
fell from 1.75 billion to 107 million per second. macOS adjusts CPU clock speed with load,
so the same renderer's CPU percentage varies between runs.

The Metal comparison below used the same machine, passage and window, seven seconds of
warm-up and a fresh process per 32-second sample. The first row is commit `86c160e`
with Metal explicitly selected. The other three rows ran the same revised release binary
(`ed09a22`), which still selected tiled rendering by default.

| Renderer and visualizer | CPU, % of one core | Median physical footprint |
| --- | ---: | ---: |
| Previous Metal, Classic | 49.65% | 683.3 MiB |
| Metal with Core Animation, Classic | 5.23% | 686.4 MiB |
| Tiled, Classic | 4.06% | 132.3 MiB |
| Metal with Core Animation, Ripples at Full | 7.83% | 820.5 MiB |

All three revised runs reported zero audio underruns. A window capture of Ripples
at Full showed 58.4 distinct updates per second in the area around the cover. In that
build, most of Metal's memory cost persisted even without a moving visualizer.

On a copy of an existing library and its artwork cache, two startup scans tried to read
tags from 3,535 AppleDouble files and took 275–282 ms. With the signature check, both
scans finished in 107–112 ms, reported zero tag reads and preserved all 3,536 tracks.

The previous installed build logged four Core Audio underruns at startup. After the scanner
fix, two launches with Ripples at Full selected Metal automatically and logged zero
startup underruns. The installed player resumed its 44-track queue and scanned the same
3,536 files in 0.2 seconds, with no tags re-read.

A 48-second comparison replayed the same menus and page changes in two muted copies
of the 44-track queue on the M4 Max. Both used the same Metal executable, a fixed
audio passage, pinned sidebars and full-rate Ripples. The control used the previous
full-window painting for the transport and open menus. CPU is a percentage of one
core and memory is the macOS physical footprint.

| Workload | CPU before → after | Median footprint before → after |
| --- | ---: | ---: |
| Open menu over cover art | 34.0% → 5.8% | 1,017 → 572 MiB |
| Open submenu | 34.2% → 4.3% | 958 → 480 MiB |
| Changing pages | 12.8% → 9.2% | 1,002 → 932 MiB |
| Menus, page changes and playback combined | 20.0% → 7.4% | 963 → 573 MiB |

Across the sequence, peak CPU over one second fell from 36.1% to 17.3%. Peak
footprint fell from 1,034 to 992 MiB. Page transitions still use the full Metal
surface. Both runs advanced the audio playhead and reported zero underruns.

Four 31-second launches compared the signed releases on the same Ripples passage and
queue. After seven seconds of warm-up, the two control runs at `c1190b6` averaged
9.26% and 9.29% CPU, with median footprints of 815 and 882 MiB. The two revised runs
averaged 5.96% and 6.07% CPU, with median footprints of 288 and 406 MiB. All four
selected Metal automatically and reported zero underruns.

After installation, the signed release resumed the listener's queue with full-rate
Ripples. Over two minutes it averaged 5.94% CPU, peaked at 8.77% over one second,
and used a median 466 MiB with a peak of 889 MiB. Core Audio reported zero
underruns and zero lost frames from launch through 130 seconds.

Remaining platform checks include the following.

- CI builds and the full workspace suite on the supported Mac architectures;
- the release's steps: rustc making the `.dSYM` (`split-debuginfo = packed`) and cargo putting
  it in `target/dist/`, `strip`, `codesign`, `hdiutil` on a CI runner, the minimum-OS check;
- the app itself: the window's traffic lights, audio device changes, hardware media keys,

  Dock, the folder watcher, tag editing, the icon in the Dock and Finder, first launch through
